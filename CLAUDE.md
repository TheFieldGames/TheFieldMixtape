# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is not a software project in the usual sense — it's the source for **TheFieldMixtape**, a Thunderstore package (mod) for the game **PEAK**. It's a crowd-sourced playlist consumed by the `onlystar-sPEAKer` mod, which plays `.ogg` tracks in-game. The repo root *is* the package: everything at root (minus dot-prefixed files/dirs) gets zipped and uploaded to Thunderstore.

It now *also* hosts the source for `.contribute-app/`, a small Node/Express web app that lets a trusted friend group add tracks without a PR — see "The contribute-app web application" below. That subdirectory is dot-prefixed specifically so it's excluded from the Thunderstore package (verified empirically, see that section).

## Layout

- `README.md` — the numbered tracklist, between `<!-- TRACKLIST:START -->`/`<!-- TRACKLIST:END -->` sentinel comments. Auto-generated (by the app now; historically by `.github/workflows/sync-tracklist.yml` on PRs) from whatever `.ogg` files currently exist — don't hand-edit the list itself.
- `my mixtape/` — one `.ogg` file per track, plus `mixtape.json` (mixtape display metadata: `name`, `author`, consumed by the sPEAKer mod at runtime). **These `.ogg` files are legacy/vestigial as of the R2 migration** (see below) — they're still git-tracked and still get zipped into the package (via `thunderstore.toml`'s `[[build.copy]]`), but going forward, new tracks added via the app live in Cloudflare R2, not here. Don't add new tracks to this folder directly; that's what the app is for.
- `icon.png` — Thunderstore listing icon. Must stay a 256x256 PNG.
- `sPEAKer.json` — currently empty; reserved by the sPEAKer mod loader.
- `thunderstore.toml` — **new**, replaces the old GitHub Actions `with:` block as the source of truth for package metadata (namespace, name, description, dependencies, communities, categories, build file mappings). Read by `tcli` directly (see below). Update namespace/name/deps/communities/categories *here*, not anywhere else.
- There is **no `manifest.json`** in this repo on purpose. `tcli build` auto-generates one from `thunderstore.toml`'s `[package]` fields. A committed one would collide with the CLI-generated one at the package root and break the build. Do not add one back.
- `.contribute-app/` — the web app (see its own section below). Dot-prefixed so it's excluded from the Thunderstore package.
- `MixTapeWebPlan.md` (**untracked, gitignored, local-only**) — the full design history/decision log for the web app, far more detailed than this file. If it's missing from your working directory, it never made it to this machine/clone and this CLAUDE.md is the only summary left; ask the user before assuming any design detail not written here.
- `PLAN.md` (**untracked, gitignored, local-only**) — separate, unrelated notes about a copyright-risk concern: most of the 56+ tracks already in `my mixtape/` are uncleared commercial music. Not acted on. The R2 migration (below) was partly motivated by this (decouples "how many tracks" from "how big/slow is every git operation"), but does **not** address the underlying copyright exposure — that's a deliberately separate, not-yet-triggered decision (a full git-history purge via `git filter-repo`/BFG).

## Publishing: `thunderstore.toml` + the contribute-app, not GitHub Actions

**`.github/workflows/main.yml` has been deleted.** There is no longer a CI pipeline that auto-publishes on push to `main`. Publishing is now done directly by `.contribute-app` calling `tcli` (Thunderstore's official CLI), one track submission at a time. If you're looking for "what happens when someone pushes to main" — the answer is now "nothing publishes automatically," which is a deliberate, load-bearing change from the old behavior. Do not reintroduce an Actions-based publish workflow without understanding this app now owns that responsibility.

Mechanics (implemented in `.contribute-app/src/publish.js` + `tcli.js`):
- The app always builds first (`tcli build --config-path thunderstore.toml --package-version X.Y.Z`), then publishes the exact resulting zip (`tcli publish --config-path thunderstore.toml --file <that zip>`) — verified that `--file` skips tcli's internal rebuild entirely. This exists so the app can measure the exact package size before upload (see bandwidth tracking below), not just as an optimization.
- Version numbers still come from git tags (`vX.Y.Z`, patch-bumped from the highest existing tag via `git ls-remote --tags`), computed by the app inline — no GitHub Actions tag-bump action anymore.
- `TCLI_AUTH_TOKEN` is read by `tcli` from the environment natively (never passed as a CLI flag, so it never appears in a process listing).

**Known consequence, not yet fixed**: `.github/CONTRIBUTING.md` (the legacy PR-based contribution flow for outside/non-trusted contributors) still says "a maintainer merges your PR and the mixtape republishes" — that's false now. `.github/workflows/sync-tracklist.yml` still works (regenerates the README on PRs touching `my mixtape/**`), but nothing publishes after a merge anymore. `CONTRIBUTING.md` needs a rewrite to either retire that flow or note a maintainer must manually publish afterward. Flagged repeatedly, not yet done as of this writing.

## The contribute-app web application (`.contribute-app/`)

A password-gated Node/Express app so a small trusted friend group can add tracks without git/GitHub knowledge, without a PR, and with immediate (not batched) publishing. Full design rationale and decision history lives in `MixTapeWebPlan.md` — this section is the load-bearing summary.

**Current status as of this writing (2026-08-23)**: fully built, unit-tested (270 tests, `npm test`), committed, and pushed — this is a real ongoing tool now, not a local prototype. Real production publishes *and* real track deletions have both happened via the live app (see git log, e.g. `075fc3f Remove track: ...`). Git history also shows a working Render Blueprint was set up and iterated on (service renamed, Docker context path fixed, auto-deploy scoped to `.contribute-app/**` only) — treat it as deployed; confirm with the user if it matters for the task at hand. Everything from the original roadmap is built except slice 4 (publish history log) — see "Remaining work" below. As of this writing the working tree is clean (everything committed and pushed) — but check `git status` at the start of a session anyway rather than assuming; this repo has a standing rule of never committing/pushing without the user explicitly asking in that turn, so finished work can sit uncommitted for a while.

**Routing**: `GET /` now serves one merged Side A/B page (previously two separate pages — `/` for the upload form, `/tracks` for the list — merged during the redesign below). `GET /tracks` redirects to `/` for old links/bookmarks. `POST /submit`, `POST /tracks/delete`, `POST /tracks/undo-delete`, `POST /tracks/publish` are unchanged.

**Cassette visual redesign**: the app was reworked from a plain form UI to a dark, cassette-tape-themed one, per `design/field-mixtape-design-spec.md` (the spec doc — read this first before touching any view/CSS) and four `field-mixtape-*.html` mockups, all committed at repo root (safe there — `thunderstore.toml`'s `[[build.copy]]` is an explicit allowlist, so `design/` is never swept into the Thunderstore package). Fixed dark theme, no light/dark toggle (deliberate). Signature component: a cassette-shell `.container` card (hub circles + a rotated cream label strip with an orange→red gradient stripe). Typography is font-per-purpose and deliberately scoped — Kalam only inside the label strip, Archivo Black only for the Side A/B letter badge, IBM Plex Mono for numbers/timers/monospace data, Inter for everything else; don't reuse Kalam elsewhere (an earlier draft put it on a modal `<h2>` and that got reverted). `GET /` is a two-panel layout: Side A is the live tracklist with inline × (mark for removal) / ↺ (undo) actions right on each row — no confirm dialogs, since undo makes it reversible; Side B is the file-queue panel (multi-file picker → a per-file title/artist mini-form guessed from the filename, editable → "+ Add to queue", looped one call at a time against the existing single-file `/submit` endpoint) plus Adding/Removing lists mirroring the batch. A sticky bottom "batch bar" shows the quota gauge, a `+N additions / −N removals / → M after publish` summary, Publish, and Clear batch (client-side loop over the existing per-item cancel/undo endpoints — no new batch-clear route). A persistent "deck bar" above both panels is the single-user lock UI, rebuilt to match `design/field-mixtape-lock.html` **exactly** per explicit request: "Nobody's/You're/`<name>` is recording" as the primary status line in IBM Plex Mono, a second muted sub-line in Inter underneath it (`.deck-sub`, e.g. "Editing is unlocked for you. Ends automatically after 5 minutes idle."), and the elapsed timer positioned in the **right-hand button group** next to Stop/Start editing — not next to the status text on the left, which is where it started and where "placement" complaints were pointing.

**CSS gotchas hit and fixed this session — worth remembering before touching `public/style.css` again**:
- A bare `button[type="submit"]` selector in a base rule is *more specific* than a single class (element+attribute beats one class in the cascade), so `button[type="submit"] { background: var(--stripe-red); ... }` was silently red-filling every ×/↺ icon button and the log-out button app-wide (they're all real form submits). Fixed by scoping the red fill to `.btn-primary` only. Never reintroduce a bare `button[type="submit"]` rule.
- A class that sets `display` (e.g. `display: flex`) on an element that's also toggled via the `hidden` DOM property needs its own explicit `.that-class[hidden] { display: none; }` override — author CSS always wins over the browser's built-in `[hidden] { display: none }`, regardless of specificity. Bit us with `.btn-rec` (the Start-editing button stayed visible after JS set `hidden = true`). Same pattern already existed correctly for `.modal-overlay`, `.idle-warning`, `.t-row`, `.staged-list` — check for this whenever a new toggleable element gets its own `display` rule.
- The base `form { margin-top: 1.5rem; ... }` rule applies to *every* `<form>`, including tiny `.inline-form`-wrapped ones (log-out, every per-row ×/↺ action form) — `.inline-form` only overrode `display`, not margin, so these all silently picked up a stray 24px top margin that threw off vertical centering wherever they sat in a flex row. `.inline-form` now also resets `margin: 0`.

**Logout now releases the edit lock**: previously, logging out while holding the lock left it stuck — the same person logging back in gets a fresh `sessionId` (minted at login) that can't match the old one, so they'd be locked out of their own session until the 5-minute idle auto-expiry. `handleLogout` (`src/auth.js`) now takes an optional `lockStore` dependency and releases the caller's lock (if held) before clearing the session, wired through a new `createAuthRouter(lockStore)` factory in `routes/auth.js` (previously a plain default-exported router with no way to reach the lock store).

**Discord notifications** (`src/discord.js`): posts to a Discord webhook on every login (tags admin/demo sessions distinctly) and every real (non-dry-run) publish (lists added/deleted tracks + version + Thunderstore link). Both are fire-and-forget — a broken/unreachable webhook must never block or fail a login or publish, so every failure is caught and logged, never thrown. `DISCORD_WEBHOOK_URL` is optional; unset means notifications are silently skipped, same pattern as other optional integrations in this app.

**Discord relay Worker — read this before touching Discord notifications again.** As of 2026-08-23, notifications no longer POST to Discord directly from Render. Root cause, found the hard way over a long debugging session: Render's shared outbound IP got caught in a **Cloudflare Error 1015 block on `discord.com` itself** — not a Discord API rate limit at all. The giveaway was the response body: once `src/discord.js` was changed to log the *entire* raw 429 response (not just a curated `retry_after`/`global` pair), it turned out to be a Cloudflare HTML "You are being rate limited" page, not Discord's JSON. Confirming evidence: swapping to a brand-new webhook produced the exact same, continuously-counting-down `retry_after` (~21.5 hours) — proving the block was scoped to the source IP, not the webhook credential. No retry/backoff logic can route around an IP ban, and Render's own dedicated-IP add-on is $100/month, wildly disproportionate here.

**The fix**: `.contribute-app/discord-relay-worker/` is a separate, minimal Cloudflare Worker (its own `wrangler.toml`, deployed independently via `npx wrangler deploy` from inside that directory — **not** part of the Express app's own deploy) that posts to Discord from Cloudflare's own edge network instead of Render's IP. It holds the real Discord webhook URL as its own Worker secret (`DISCORD_WEBHOOK_URL`, set via `wrangler secret put`, never passed in by the caller) and gates every request behind a second shared secret (`RELAY_SECRET`, checked against an `X-Relay-Secret` header) — so even if the Worker's public URL leaks, it can only ever relay to this one preconfigured webhook, never act as an open relay to anywhere an attacker chooses.

`src/discord.js`'s `postToDiscord` takes `relayUrl`/`relaySecret` (env: `DISCORD_RELAY_URL`/`DISCORD_RELAY_SECRET`) and, when both are set, POSTs to the relay instead of straight to `webhookUrl` — fully backward compatible, falls back to the old direct-webhook behavior when unset. As of this writing both are set on Render, and `DISCORD_WEBHOOK_URL` is no longer needed there at all (only the Worker needs it now) — safe to remove from Render's env if it's still lingering.

Deploying/managing the Worker needs its own Cloudflare credentials, separate from the R2 ones: `CLOUDFLARE_API_TOKEN` (a token scoped to just `Workers Scripts: Edit` + a couple of read-only permissions — see the git history around 2026-08-23 for the exact minimal permission set used) and `CLOUDFLARE_ACCOUNT_ID` (same Cloudflare account as R2, so this can just be copied from the existing `R2_ACCOUNT_ID`). Both live in the local `.env` for `wrangler` to use; neither is needed by the Express app itself at runtime. `.contribute-app/discord-relay-worker/.wrangler/` (wrangler's local build cache) is gitignored — never commit it.

**Architecture**:
- Audio storage: Cloudflare R2 (S3-compatible, free at this scale, zero egress fees), not git, going forward. Bucket key convention: `my mixtape/<Title> - <Artist>.ogg` (matches the package's internal zip layout). `src/storage.js`.
- Git is still used, but only for the lightweight stuff: cloning `main` for `README.md`/`thunderstore.toml`/etc., committing the regenerated README, tagging the version, pushing. Every clone is fresh and always sources from `main` specifically (`publish.SOURCE_BRANCH`), regardless of where the result gets pushed — `git clone --branch <name>` requires that branch to already exist remotely, and the push target (`config.branch`) can be a disposable not-yet-existing local-dev branch.
- **`tcli publish` is the first permanent step, not the last** (redesigned 2026-08-25 — see `MixTapeWebPlan.md`). Everything up through `tcli build` — clone, README regen, local commit/tag, the build itself — touches nothing permanent for either a dry run or a real publish: real R2 is only ever *read*, never mutated, and the resulting track list is always computed in-memory (the same technique a dry run always used). Only *after* a real `tcli publish` call succeeds does `processPublish` promote/delete R2 objects, push git, and update the manifest. This eliminated the old "committed but not published" partial-failure category entirely — a failed publish now always leaves genuinely nothing changed, so retrying is just re-running the whole pipeline from a clean slate. If something fails *after* `tcli publish` already succeeded (the R2/git/manifest bookkeeping that follows), that's reported as `bookkeepingError` on an otherwise-successful result — Thunderstore already has the update regardless, only this app's own records might lag behind. `CANCEL_CUTOFF_STAGE` (in both `src/publish.js` and `src/jobs.js`, the latter importing it from the former — no longer independently duplicated) is `"tcli-publish"`, not `"push-branch"` — that's the actual point of no return now.
- One in-process mutex (`src/queue.js`, `runExclusive`) serializes all submissions — required because the app must run as exactly one instance (no horizontal scaling) for this to be correct. Render's free/Starter plans do this by default.
- **Dry run**: a checkbox that runs the entire real pipeline except the final `tcli publish` — isolated via a separate R2 key prefix (`dry-run/`), a separate fixed git branch (`contribute-app-dry-run`, force-pushed/reused), and a separate tag prefix (`dryrun-`) so it can never pollute the real track library, git history, or version sequence. Safe to use even against production.
- **Limits**: 50 tracks max (checked twice — early, and again immediately before the real publish as a final safety net; lowered from 70 on 2026-08-24 as a partial mitigation for `tcli` OOM-crashing on Render's 512MB container during upload — helps but doesn't reliably fix it on its own, see `MixTapeWebPlan.md`), 8000KB max per converted `.ogg` file.
- **Monthly bandwidth tracking** (`src/bandwidth.js`): Render's free/Hobby tier caps *outbound* bandwidth at 5GB/month, per-workspace (verified directly against Render's docs — a "100GB" figure exists in older sources but was the *legacy* plan, force-migrated away 2026-08-01). Every `tcli publish` uploads the *entire* package (Thunderstore versions are immutable, complete zips, not diffs) — that's the actual bandwidth consumer, not the R2 download (which is inbound to Render and doesn't count). The app locks out real publishing at 4.5GB (deliberate safety margin) tracked via a `bandwidth-usage.json` object in R2, resets on the calendar month. `config.trackBandwidth` (env: `DISABLE_BANDWIDTH_TRACKING`) lets a *local* instance opt out entirely — Render's cap only meters Render's own servers, so a real publish run from a non-Render machine structurally can't consume any of it; safe-by-default (tracking stays on unless explicitly disabled), opt-out is only appropriate in a local `.env`, never on Render itself.
- Logging: `src/logger.js`, plain timestamped stdout/stderr — deliberately no logging library, since Render captures container stdout/stderr automatically with zero setup. Every submission stage logs with elapsed time; the whole pipeline takes 1-2 minutes in production (dominated by git clone + ffmpeg conversion, not R2).

**Built** (all of it — see `MixTapeWebPlan.md` for the full design/verification writeup of each): a persistent R2-backed track manifest (`manifest.json`, tracks + `pendingDeletes` + `publishLog`), a track list page, deleting tracks (marks pending, removed at publish time), queueing multiple adds/deletes before one batched publish, a live SSE progress modal, a single-user edit lock, and the cassette visual redesign / Side A/B merge described above. Legacy tracks that predate the manifest are backfilled with `"addedBy": "TEMP"` (the user knows the real authors and will correct them individually — not a claim they're unknown).

**Remaining work**:
- **Publish history log** (the one piece of the original 4-slice roadmap not yet built): append an entry to the manifest's `publishLog` array on every successful publish (version, timestamp, added/deleted tracks — the data `processPublish` already computes, just not persisted), add a `GET /history` route to render it. Not started — the only item left on the original roadmap.

Everything else from earlier rounds of this list — lock-status polling pausing on idle, the logout/lock-release bug, the batch bar covering page content, keeping the edit lock alive through a publish, the one-click demo login, `.mp3`-only upload validation, the favicon, the Thunderstore link, and the Discord notification system (including the relay Worker above) — is built, tested, and live as of 2026-08-23.

## Local dev environment notes (this machine specifically)

No Node/Docker/ffmpeg/tcli were preinstalled when this was set up. If continuing on this same machine: a portable Node 20 install lives at `~/.local/node` (added to `PATH` via `~/.zshrc`), and `ffmpeg`/`tcli`/`gh` binaries live at `~/.local/bin` (also on `PATH`). `wrangler` (Cloudflare's CLI, needed for the Discord relay Worker above) isn't installed globally either — use `npx wrangler ...`, no install needed. `.contribute-app/.env` (gitignored) already has real local credentials filled in, with `DISABLE_BANDWIDTH_TRACKING=true` and `GIT_TARGET_BRANCH=contribute-app-test` set for safe local testing — `GIT_TARGET_BRANCH` only affects git push target, not R2 or Thunderstore, so a real (non-dry-run) local submission still really publishes. Run locally with `npm run dev` (loads `.env` via Node's native `--env-file`, no dotenv dependency).

`.env` also now carries, alongside the original R2/git/Thunderstore credentials: `DISCORD_WEBHOOK_URL` (currently commented out locally — see below), `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` (deployment credentials for `discord-relay-worker/`, not used by the Express app itself), and `DISCORD_RELAY_URL`/`DISCORD_RELAY_SECRET` (point the local app at the same relay Worker Render uses). `DISCORD_WEBHOOK_URL` is commented out in the local `.env` specifically so a local dev server never independently posts to the real Discord webhook while testing — it shares the same webhook/rate-limit bucket as production, and having two instances (or more, across repeated local test runs) hitting it concurrently was part of the mystery during the 429 debugging session above before the real (IP-block) root cause was found. Leave it commented out; re-enable only if you specifically need to test Discord notifications locally, and prefer routing through the relay (`DISCORD_RELAY_URL`) over the direct webhook even then.
